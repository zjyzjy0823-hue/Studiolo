# 会话层架构评审（2026-11-24）

## 0. 先说一个事实

手机上此前装的是 **0.8.6（versionCode 8006，11-23 22:42 安装）**。
0.8.7（续传）、0.8.8（外链下载）、0.8.9（下载记录）、0.9.0（两个入口）**都没装到手机上**。
刚才已用 adb 装上 0.9.0。

所以「没有下载页」「文件没了」这类症状，至少一部分是版本问题，不是架构问题。
下面只列**架构层面确实存在的问题**。

## 1. 症状 → 根因（按层归位）

| 症状 | 直接原因 | 层级 |
|---|---|---|
| 退出再回来，下载记录/文件没了 | 下载记录只存 `localStorage`（`downloadHistory.ts`），没有服务端副本；换设备/清数据即丢 | 客户端存储 |
| 用时「未记录」 | `durationMs` 由客户端 `promptMeta.startedAt` 现算（`fleet.ts:2549`），重连/重启后这个内存对象没了 | 客户端内存 |
| 多轮主动对话不显示工具调用 | 工具调用只作为**事件帧**（`tool_call`/`tool_call_update`）存在节点内存 `_history[sid]`（deque，`_HISTORY_LIMIT` 上限）；节点重启或超出上限后，从 gateway transcript 重建时只能还原一部分 | 节点状态 |
| 老是重连 | WS 心跳/空闲断开后客户端按 500/1000ms 重试；节点或 Core 任一重启即触发一轮，且重连后要重放历史 | 通道 + 状态恢复 |
| 各种插话有问题、丢对话 | 插话要跨四层（客户端判定 → Core 白名单 → 节点校验 → adapter steer），任一层状态不同步（`_active_runs` 与真实运行态不一致）就降级成普通发送或失败 | 协议语义 |
| 客户端出现不该出现的消息 | Hermes gateway 把「后台进程已完成」这类系统通知以 **user 角色**写入会话历史，客户端照实渲染成用户气泡 | 会话写入入口 |

**共性**：这些都不是 UI bug，而是**状态放在哪、谁是事实源**的问题。

## 2. 当前架构的结构性问题

1. **多事实源并存**
   - 节点内存 `_history[sid]`（有界 deque）
   - gateway `session.transcript`（持久）
   - 客户端 store（`sessionsByKey` / `messages` / `promptMeta`）
   三者各自演化，靠 seq/游标/快照去对账。任何一方丢一段，就出现"看不见工具调用""用时缺失""运行态永久三点"。

2. **显示态依赖客户端内存**
   用时、流式状态、待发件箱、插话挂起，都是 client-only。重启=清零。

3. **事件流没有持久化边界**
   增量帧只在传输层有意义，没有落地成可重放的日志；节点重启后靠"从 transcript 反推"，反推是**有损的**。

4. **系统消息与用户消息同源**
   `[IMPORTANT: Background process ... completed]` 以 user 角色写入 → 客户端无法区分"用户说的"和"系统注入的"。

## 3. 目标架构（重构范围）

一句话：**服务端是唯一事实源，客户端只是投影；所有显示态都由事件派生。**

```
节点/网关 ──(append)──> 会话事件日志（SQLite，append-only，带 seq/turn_id）
                                │
                                ├─ fold → 会话快照（messages、tool_calls、timing、running、attachments）
                                └─ 订阅：seq > cursor 的增量
客户端：拉快照 → 渲染；订阅增量 → 追加；断线 → 带 cursor 续传（缺帧自动补）
```

具体四条：

1. **事件日志落地**
   每个会话一条 append-only 日志（SQLite 表 `session_events`：`session_id, seq, turn_id, type, payload, created_at`），所有事件（user/assistant/tool_call/tool_result/approval/notice/attachment）都写进去。
   → 节点重启不再需要"从 transcript 反推"，直接读日志。

2. **快照 = 折叠结果**
   `GET /sessions/{id}/snapshot?since=seq` 返回：消息列表 + 每个 turn 的 `startedAt/endedAt/toolCalls` + 运行态 + 附件。
   → 用时、工具调用、运行态全部由服务端给，客户端不再自己算。

3. **系统通知独立事件类型**
   `notice` 类型单独渲染（灰条/系统卡），永不进 user 气泡；后台进程完成、审批结果、重连提示都走它。

4. **客户端降级为投影层**
   `fleet.ts` 拆成三块：`transport`（WS + 重连 + 游标）、`projection`（事件 → 只读状态）、`outbox`（用户操作队列）。
   删掉现在散落的"补流/抢占/指纹回退"逻辑——它们存在的前提是没有服务端日志。

## 4. 迁移顺序（每步可独立上线）

| 阶段 | 内容 | 可验证结果 |
|---|---|---|
| **P1** | `session_events` 表 + 写入点（节点/网关两侧所有事件） | 断网 5 分钟后重连，工具调用完整 |
| **P2** | snapshot 接口 + 客户端改用 snapshot 渲染 | 冷启动即显示用时/工具调用，不再"未记录" |
| **P3** | `notice` 事件类型 + 客户端渲染 | 后台通知不再冒充用户消息 |
| **P4** | 下载记录改为服务端表（`downloads`） | 换设备仍能看到历史 |
| **P5** | 删除旧补丁路径（缓冲/抢占/指纹） | 代码量下降，回归用例全绿 |

## 5. 工作量与风险

- P1–P2 是主菜：**约 3–5 天**（含测试），不动 UI 视觉，只换数据通路
- P3/P4 各半天
- P5 是删代码，风险最高处是"删早了"，所以放最后
- 数据迁移：现有 `state.db` 的 messages 可以一次性回填成事件（迁移脚本 + 对账）
- **不建议整体重写 UI**：UI 层的问题都能用 P2 的数据修掉，重写 UI 成本远大于收益

## 6. 结论

是架构问题，但不是"整个 App 要重写"，而是**会话状态的归属错了**：
现在状态活在三个地方（节点内存 / 客户端内存 / gateway 历史），应该收敛成"一个日志 + 一个快照"。

按 P1→P5 做，等于把会话层重写一遍，UI 和 Rust 壳不动。
